# Uniezz — Авторизация

## Обзор

Uniezz проверяет, что пользователь — реальный действующий студент, прежде чем дать доступ. Пять вузов, три провайдера идентификации, одна точка входа на **Go API** для веба и мобильного клиента.

| Вуз | Провайдер | Верифицированные данные |
|-----|-----------|-------------------------|
| **UMCS** | USOS API (OAuth 1.0a) | Личность, факультет, направление, курс |
| **Politechnika Lubelska** | Microsoft Entra ID (OIDC) | Личность, вуз; факультет, если опубликован |
| **Uniwersytet Przyrodniczy** | Microsoft Entra ID (OIDC) | Личность, вуз; факультет, если опубликован |
| **KUL** | Microsoft Entra ID (OIDC) | Личность, вуз; факультет, если опубликован |
| **WSEI** | Microsoft Entra ID (OIDC) | Личность, вуз; факультет, если опубликован |
| *любой из пяти* | Email OTP | Только университетский домен — запасной вариант |

### Рассмотренные варианты

| Вариант | Решение |
|---------|---------|
| **USOS API (OAuth 1.0a)** | Выбран для UMCS. Официальный, верифицированные данные, самостоятельная регистрация |
| **Microsoft Entra ID (OIDC)** | Выбран для остальных четырёх. Все пять вузов имеют тенанты Entra |
| **Email OTP по университетскому домену** | Запасной вариант, если админ вуза блокирует согласие на приложение |
| Moodle Web Services | Отклонён. Токен выдаётся вручную IT-отделом вуза |
| Парсинг формы входа кампуса | Отклонён. Обработка университетских паролей — юридический риск и угроза безопасности |

## Провайдер 1 — UMCS через USOS API

UMCS работает на **USOS** — системе управления учебным процессом, которую используют более 50 польских вузов, — и предоставляет публичный **USOS API**. Это единственный люблинский вуз в официальном реестре инсталляций USOS API.

### Регистрация приложения

Самообслуживание — без процедуры одобрения и без договора с вузом.

1. Открыть https://apps.umcs.pl/developers/
2. Указать название приложения, опционально адрес сайта и действующий email для связи
3. Получить **Consumer Key** и **Consumer Secret**

Consumer Secret не покидает бэкенд и не попадает в репозиторий. По тому же адресу есть форма отзыва ключа, подтверждение приходит на зарегистрированный email.

### Поток OAuth 1.0a

USOS API использует OAuth 1.0a (трёхэтапный), не OAuth 2.0. Вся подпись запросов выполняется на бэкенде через HMAC-SHA1.

| Шаг | URL |
|-----|-----|
| Request token | `https://apps.umcs.pl/services/oauth/request_token` |
| Authorize | `https://apps.umcs.pl/services/oauth/authorize` |
| Access token | `https://apps.umcs.pl/services/oauth/access_token` |

1. **Request token** — бэкенд обращается к `request_token` с Consumer Key, списком `scopes` и `oauth_callback` на Uniezz
2. **Редирект** — пользователь попадает на `authorize` и вводит свои данные UMCS на странице университета
3. **Согласие** — пользователь подтверждает права; USOS возвращает его с `oauth_token` и `oauth_verifier`
4. **Access token** — бэкенд обменивает verifier на долгоживущий токен доступа и его секрет
5. **Получение профиля** — бэкенд вызывает API с подписанным токеном и создаёт или обновляет аккаунт Uniezz

Пароль UMCS вводится только на странице UMCS и никогда не виден Uniezz.

### Права доступа (scopes)

Ни одно из них не требует одобрения администратора.

| Scope | Назначение в Uniezz |
|-------|---------------------|
| *(по умолчанию)* | Базовая идентификация — ID пользователя, имя и фамилия |
| `studies` | Программы, курсы, списки групп — источник факультета, направления и года обучения |
| `email` | Университетский адрес, используется как идентификатор аккаунта |
| `photo` | Фото профиля и настройки его видимости |
| `personal` | Дата рождения — возрастные ограничения, дни рождения, возрастные фильтры в «Знакомствах» |
| `offline_access` | Долгоживущий токен для обновления профиля между сессиями |

**О скоупе `personal`:** он запрашивается ради даты рождения, которая нужна Uniezz для возрастных ограничений и фильтров по возрасту в модуле «Знакомства». Тот же скоуп возвращает PESEL и другие идентификаторы — они отбрасываются при чтении и никогда не пишутся в базу и в логи.

**Сознательно не запрашиваются:** `grades`, `payments`, `mobile_numbers`. Продукту они не нужны, а их запрос снижает долю согласий.

### Получаемые данные

Читаются через `services/users/user`, где параметр `fields` явно перечисляет каждое поле (USOS API это требует): ID пользователя, имя и фамилия, университетский email, дата рождения, программы обучения, статус студента, URL фотографии. Данные факультета определяются по программе через соответствующие эндпоинты. Точный набор полей фиксируется на этапе интеграции по https://apps.umcs.pl/developers/api/

## Провайдер 2 — Entra ID для остальных четырёх

Все пять вузов имеют тенанты Microsoft Entra ID — проверено через эндпоинт обнаружения тенантов Microsoft. Для четырёх вузов без публичного академического API Entra — сильнейшее доступное подтверждение: оно подтверждает живой аккаунт в каталоге вуза, а не просто владение почтовым адресом.

### Тенанты

| Вуз | Домены | Tenant ID | Тип |
|-----|--------|-----------|-----|
| Politechnika Lubelska | `pollub.edu.pl`, `student.pollub.edu.pl` | `dbb41d7a-0043-4ee2-9843-6e4ff66cc9c8` | Managed |
| Uniwersytet Przyrodniczy | `up.lublin.pl`, `student.`, `stud.` | `25a59194-f151-40c5-9e45-365a4d46d7b9` | Managed |
| WSEI | `wsei.lublin.pl`, `student.`, `stud.` | `bab1e1e4-b3e8-49c1-93e4-eaeff72f1f5d` | Managed |
| KUL — студенты | `student.kul.pl` | `f445c1ee-43fc-42e8-b642-b382d382c3c1` | Managed — **допускается** |
| KUL — сотрудники | `kul.pl` | `7952c9f0-b177-4a4c-ab55-7c2f5ab0808d` | Managed — **отклоняется** |
| UMCS | `umcs.pl` | `80dbd34a-9b20-490b-ac49-035af103ab2b` | Federated (свой SAML IdP) |

У KUL два отдельных тенанта, и это единственный вуз, где студенты уже отделены на уровне тенанта: студенческий допускается, тенант сотрудников отклоняется. UMCS указан для полноты — он авторизуется через USOS.

### Настройка

Регистрируется одно **multi-tenant** приложение в Entra ID, затем разрешаются только tenant ID, помеченные выше как допускаемые. Пользователь, чей `tid` не в списке, отклоняется — это ограничивает вход люблинскими вузами.

### Только студенты

Uniezz — студенческая платформа, аккаунты сотрудников входить не должны. Одного tenant ID для этого недостаточно: Politechnika Lubelska, Uniwersytet Przyrodniczy и WSEI держат студентов и сотрудников в одном тенанте. Ограничение многослойное:

1. **Белый список тенантов** — полностью решает вопрос по KUL, чьи студенты живут в отдельном тенанте
2. **Домен UPN** — там, где вуз выдаёт студенческую почту на поддомене (`student.`, `stud.`), допускаются только такие адреса
3. **Атрибуты каталога** — проверяются `employeeType` и `jobTitle` из Graph; значение, указывающее на сотрудника, отклоняется
4. **Ручная проверка** — если ни один из шагов выше не дал ответа, аккаунт создаётся с урезанными правами и помечается на проверку

Шаги 2 и 3 зависят от того, как именно каждый вуз заводит аккаунты, а это не выяснить без живого аккаунта. Пока это не подтверждено по каждому вузу, разделение студентов и сотрудников гарантированно работает только для KUL и — через `student_status` — для UMCS.

### Гарантированные claims

Доступны из ID-токена без дополнительных запросов:

| Claim | Применение |
|-------|-----------|
| `oid` | Стабильный ID пользователя внутри тенанта — первичный ключ |
| `tid` | ID тенанта — определяет вуз однозначно |
| `name` | Имя и фамилия |
| `preferred_username` | UPN, обычно университетская почта |
| `email` | Почта, если опубликована администратором; иначе используется UPN |

### Дополнительные поля профиля

Запрашиваются из Microsoft Graph со scope `User.Read`, на который согласие даёт сам пользователь — администратор не участвует. В ответе `/me` по умолчанию **нет** поля `department`, поэтому нужен `$select`:

```
GET https://graph.microsoft.com/v1.0/me?$select=id,displayName,mail,userPrincipalName,jobTitle,department,companyName,officeLocation,employeeType
```

- `department` — обычно факультет
- `jobTitle`, `employeeType` — иногда «Student»
- `companyName` — название вуза
- `officeLocation` — здание или кампус
- `GET /me/photo/$value` — фото профиля, тот же scope
- `birthday` — дата рождения; в схеме есть, но у студентов почти никогда не заполнена, поэтому считаем её заявленной пользователем при онбординге

Эти поля заполняет администратор вуза при создании аккаунта. Они могут быть заполнены полностью или пусты, и у каждого тенанта по-своему. Проверить это можно только одним живым студенческим аккаунтом на вуз.

**Недоступно никогда:** год обучения, номер группы, семестр, оценки. Эти данные живут в системах деканатов (eHMS, Wirtualny Dziekanat, e-KUL), ни одна из которых не имеет публичного API.

## Провайдер 3 — Запасной Email OTP

Используется, если администратор вуза отключил согласие пользователей на сторонние multi-tenant приложения — тогда вместо экрана согласия Entra возвращает «Need admin approval».

1. Пользователь вводит университетский email; домен сверяется с белым списком
2. Генерируется шестизначный код; сохраняются его хеш, email и срок действия
3. Код отправляется письмом; пользователь вводит его
4. Проверяются хеш, срок и счётчик попыток; выдаётся сессия

Лимиты: 3 кода на email в час, 10 на IP в час, 5 попыток до сжигания кода. Подтверждает только владение доменом — факультет и курс остаются заявленными самим пользователем.

## Единый эндпоинт авторизации

Веб и мобильный клиент никогда не обращаются к USOS, Entra или почтовому провайдеру. Они работают с одним Go API Uniezz, который внутри направляет запрос нужному провайдеру.

### Публичный API

| Маршрут | Назначение |
|---------|-----------|
| `POST /auth/start` | Тело: `{ university, provider? }`. Возвращает URL редиректа выбранного провайдера или запускает поток OTP |
| `GET /auth/callback/:provider` | Единая точка обратного вызова. Обрабатывает verifier от USOS, код авторизации Entra и ввод OTP |
| `GET /auth/me` | Профиль текущей сессии |
| `POST /auth/logout` | Очищает сессию Uniezz |

`:provider` — одно из `usos`, `entra`, `otp`.

### Интерфейс провайдера

Каждый провайдер реализует один и тот же контракт:

```
AuthProvider {
  start(university)  -> URL редиректа или challenge
  callback(params)   -> NormalizedProfile
}
```

### Нормализованный профиль

Все провайдеры возвращают одну структуру, поэтому остальное приложение не ветвится по вузам:

```
NormalizedProfile {
  provider          usos | entra | otp
  providerUserId    стабильный ID от провайдера
  universityId      umcs | pollub | up | kul | wsei
  email
  firstName, lastName
  photoUrl?
  birthDate?        верифицирована из USOS, иначе заявлена пользователем
  faculty?          верифицирован, выведен или null
  programme?
  yearOfStudy?      только UMCS
  verification      verified | directory | domain
}
```

### Уровни верификации

| Уровень | Значение | Источник |
|---------|----------|----------|
| `verified` | Подтверждена академическая запись | USOS API — UMCS |
| `directory` | Живой аккаунт в каталоге вуза | Entra ID — остальные четыре |
| `domain` | Только владение университетской почтой | Email OTP |

Уровень хранится в профиле и отображается значком. Факультет и курс помечаются как подтверждённые или заявленные по каждому полю отдельно, а не по аккаунту целиком.

### Добавление вуза

Новому вузу нужна запись провайдера и ID тенанта или инсталляции. Маршруты, работа с сессией и модель пользователя не меняются. Если Politechnika Lubelska, Uniwersytet Przyrodniczy, KUL или WSEI позже дадут доступ к USOS или Moodle API, он подключается за тем же эндпоинтом, а существующие аккаунты повышаются с `directory` до `verified`.

## Модель сессии

- Токены провайдеров хранятся только на бэкенде, браузер их не видит
- Фронтенд работает с cookie сессии Uniezz — `HttpOnly`, `Secure`, `SameSite=Lax`
- Данные профиля обновляются при входе и по запросу, а не на каждом запросе
- Выход очищает сессию Uniezz; авторизация у провайдера остаётся, пока пользователь не отзовёт её в первоисточнике

---

## Безопасность и приватность

- Consumer secret, client secret и токены доступа хранятся в зашифрованном виде и не попадают в логи
- Запрашивается минимальный набор прав, необходимый продукту
- PESEL и другие идентификаторы, приходящие вместе с датой рождения, отбрасываются при чтении и не сохраняются
- Пользователь может отвязать подключённый аккаунт и удалить профиль Uniezz
- Авторизацию у провайдера пользователь может независимо отозвать в USOSweb или в своём аккаунте Microsoft
- Обработка персональных данных соответствует GDPR: заявленная цель, минимальный объём, удаление по требованию

## Ограничения

- Год обучения верифицирован только для UMCS; в остальных случаях он всегда заявляется самим пользователем
- Поле `department` может быть пустым в любом тенанте Entra, и без живого студенческого аккаунта это не выяснить
- Администратор тенанта может заблокировать согласие пользователей, что переводит вуз на запасной OTP
- Politechnika Lubelska, Uniwersytet Przyrodniczy и WSEI держат студентов и сотрудников в одном тенанте; их разделение опирается на домен UPN или атрибуты каталога, ни одно из которых не подтверждено без живого аккаунта
- Подпись запросов OAuth 1.0a требует бэкенда; поток USOS невозможно реализовать только в браузере
- Politechnika Lubelska, Uniwersytet Przyrodniczy, KUL и WSEI работают на eHMS, Wirtualny Dziekanat и e-KUL соответственно — ни одна система не имеет публичного API

## Чеклист реализации

1. Зарегистрировать приложение USOS на https://apps.umcs.pl/developers/ и положить ключи в секреты бэкенда
2. Зарегистрировать multi-tenant приложение Entra и ограничить его перечисленными выше tenant ID
3. Построить единые маршруты `/auth` и интерфейс провайдера на Go API
4. Реализовать провайдер USOS — трёхэтапный OAuth 1.0a с подписью HMAC-SHA1
5. Реализовать провайдер Entra, затем протестировать `$select` из Graph на одном живом аккаунте каждого вуза и записать, какие поля заполнены
