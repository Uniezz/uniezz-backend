# Uniezz — Авторизація

## Огляд

Uniezz перевіряє, що користувач — реальний чинний студент, перш ніж надати доступ. П'ять вишів, три провайдери ідентифікації, одна точка входу на **Go API** для вебу й мобільного клієнта

| Виш | Провайдер | Верифіковані дані |
|-----|-----------|-------------------|
| **UMCS** | USOS API (OAuth 1.0a) | Особа, факультет, напрям, курс |
| **Politechnika Lubelska** | Microsoft Entra ID (OIDC) | Особа, виш; факультет, якщо опублікований |
| **Uniwersytet Przyrodniczy** | Microsoft Entra ID (OIDC) | Особа, виш; факультет, якщо опублікований |
| **KUL** | Microsoft Entra ID (OIDC) | Особа, виш; факультет, якщо опублікований |
| **WSEI** | Microsoft Entra ID (OIDC) | Особа, виш; факультет, якщо опублікований |
| *будь-який із п'яти* | Email OTP | Лише університетський домен — запасний варіант |

### Розглянуті варіанти

| Варіант | Рішення |
|---------|---------|
| **USOS API (OAuth 1.0a)** | Обрано для UMCS. Офіційний, верифіковані дані, самостійна реєстрація |
| **Microsoft Entra ID (OIDC)** | Обрано для решти чотирьох. Усі п'ять вишів мають тенанти Entra |
| **Email OTP за університетським доменом** | Запасний варіант, якщо адміністратор блокує згоду на застосунок |
| Moodle Web Services | Відхилено. Токен видається вручну IT-відділом вишу |
| Парсинг форми входу кампусу | Відхилено. Обробка університетських паролів — юридичний ризик і загроза безпеці |

## Провайдер 1 — UMCS через USOS API

UMCS працює на **USOS** — системі управління навчальним процесом, яку використовують понад 50 польських вишів, — і надає публічний **USOS API**. Це єдиний люблінський виш в офіційному реєстрі інсталяцій USOS API.

### Реєстрація застосунку

Самообслуговування — без процедури затвердження та без договору з вишем.

1. Відкрити https://apps.umcs.pl/developers/
2. Вказати назву застосунку, опційно адресу сайту та дійсний email для зв'язку
3. Отримати **Consumer Key** і **Consumer Secret**

Consumer Secret не залишає бекенд і не потрапляє до репозиторію. За тією ж адресою є форма відкликання ключа, підтвердження надходить на зареєстрований email.

### Потік OAuth 1.0a

USOS API використовує OAuth 1.0a (триетапний), а не OAuth 2.0. Усе підписування запитів виконується на бекенді через HMAC-SHA1.

| Крок | URL |
|------|-----|
| Request token | `https://apps.umcs.pl/services/oauth/request_token` |
| Authorize | `https://apps.umcs.pl/services/oauth/authorize` |
| Access token | `https://apps.umcs.pl/services/oauth/access_token` |

1. **Request token** — бекенд звертається до `request_token` з Consumer Key, переліком `scopes` і `oauth_callback` на Uniezz
2. **Редирект** — користувач потрапляє на `authorize` і вводить свої дані UMCS на сторінці університету
3. **Згода** — користувач підтверджує права; USOS повертає його з `oauth_token` і `oauth_verifier`
4. **Access token** — бекенд обмінює verifier на довготривалий токен доступу та його секрет
5. **Отримання профілю** — бекенд викликає API з підписаним токеном і створює або оновлює акаунт Uniezz

Пароль UMCS вводиться лише на сторінці UMCS і ніколи не видимий для Uniezz.

### Права доступу (scopes)

Жодне з них не потребує схвалення адміністратора.

| Scope | Призначення в Uniezz |
|-------|----------------------|
| *(за замовчуванням)* | Базова ідентифікація — ID користувача, ім'я та прізвище |
| `studies` | Програми, курси, списки груп — джерело факультету, напряму та року навчання |
| `email` | Університетська адреса, використовується як ідентифікатор акаунта |
| `photo` | Фото профілю та налаштування його видимості |
| `personal` | Дата народження — вікові обмеження, дні народження, вікові фільтри у «Знайомствах» |
| `offline_access` | Довготривалий токен для оновлення профілю між сесіями |

**Про scope `personal`:** він запитується заради дати народження, яка потрібна Uniezz для вікових обмежень і фільтрів за віком у модулі «Знайомства». Той самий scope повертає PESEL та інші ідентифікатори — вони відкидаються під час читання і ніколи не записуються до бази й логів.

**Свідомо не запитуються:** `grades`, `payments`, `mobile_numbers`. Продукту вони не потрібні, а їх запит знижує частку наданих згод.

### Отримувані дані

Читаються через `services/users/user`, де параметр `fields` явно перелічує кожне поле (USOS API цього вимагає): ID користувача, ім'я та прізвище, університетський email, дата народження, програми навчання, статус студента, URL фотографії. Дані факультету визначаються за програмою через відповідні ендпоїнти. Точний набір полів фіксується на етапі інтеграції за https://apps.umcs.pl/developers/api/

## Провайдер 2 — Entra ID для решти чотирьох

Усі п'ять вишів мають тенанти Microsoft Entra ID — перевірено через ендпоїнт виявлення тенантів Microsoft. Для чотирьох вишів без публічного академічного API Entra — найсильніше доступне підтвердження: воно засвідчує живий акаунт у каталозі вишу, а не просто володіння поштовою адресою.

### Тенанти

| Виш | Домени | Tenant ID | Тип |
|-----|--------|-----------|-----|
| Politechnika Lubelska | `pollub.edu.pl`, `student.pollub.edu.pl` | `dbb41d7a-0043-4ee2-9843-6e4ff66cc9c8` | Managed |
| Uniwersytet Przyrodniczy | `up.lublin.pl`, `student.`, `stud.` | `25a59194-f151-40c5-9e45-365a4d46d7b9` | Managed |
| WSEI | `wsei.lublin.pl`, `student.`, `stud.` | `bab1e1e4-b3e8-49c1-93e4-eaeff72f1f5d` | Managed |
| KUL — студенти | `student.kul.pl` | `f445c1ee-43fc-42e8-b642-b382d382c3c1` | Managed — **допускається** |
| KUL — працівники | `kul.pl` | `7952c9f0-b177-4a4c-ab55-7c2f5ab0808d` | Managed — **відхиляється** |
| UMCS | `umcs.pl` | `80dbd34a-9b20-490b-ac49-035af103ab2b` | Federated (власний SAML IdP) |

KUL має два окремі тенанти і це єдиний виш, де студенти вже відокремлені на рівні тенанта: студентський допускається, тенант працівників відхиляється. UMCS наведено для повноти — він авторизується через USOS.

### Налаштування

Реєструється один **multi-tenant** застосунок в Entra ID, потім дозволяються лише tenant ID, позначені вище як допустимі. Користувач, чий `tid` не в списку, відхиляється — це обмежує вхід люблінськими вишами.

### Лише студенти

Uniezz — студентська платформа, акаунти працівників входити не повинні. Самого tenant ID для цього замало: Politechnika Lubelska, Uniwersytet Przyrodniczy і WSEI тримають студентів та працівників в одному тенанті. Обмеження багатошарове:

1. **Білий список тенантів** — повністю вирішує питання щодо KUL, чиї студенти живуть в окремому тенанті
2. **Домен UPN** — там, де виш видає студентську пошту на піддомені (`student.`, `stud.`), допускаються лише такі адреси
3. **Атрибути каталогу** — перевіряються `employeeType` і `jobTitle` з Graph; значення, що вказує на працівника, відхиляється
4. **Ручна перевірка** — якщо жоден із кроків вище не дав відповіді, акаунт створюється з урізаними правами і позначається на перевірку

Кроки 2 і 3 залежать від того, як саме кожен виш заводить акаунти, а це не з'ясувати без живого акаунта. Доки це не підтверджено по кожному вишу, розділення студентів і працівників гарантовано працює лише для KUL і — через `student_status` — для UMCS.

### Гарантовані claims

Доступні з ID-токена без додаткових запитів:

| Claim | Застосування |
|-------|--------------|
| `oid` | Стабільний ID користувача всередині тенанта — первинний ключ |
| `tid` | ID тенанта — однозначно визначає виш |
| `name` | Ім'я та прізвище |
| `preferred_username` | UPN, зазвичай університетська пошта |
| `email` | Пошта, якщо опублікована адміністратором; інакше використовується UPN |

### Додаткові поля профілю

Запитуються з Microsoft Graph зі scope `User.Read`, на який згоду дає сам користувач — адміністратор не бере участі. У відповіді `/me` за замовчуванням **немає** поля `department`, тому потрібен `$select`:

```
GET https://graph.microsoft.com/v1.0/me?$select=id,displayName,mail,userPrincipalName,jobTitle,department,companyName,officeLocation,employeeType
```

- `department` — зазвичай факультет
- `jobTitle`, `employeeType` — іноді «Student»
- `companyName` — назва вишу
- `officeLocation` — будівля або кампус
- `GET /me/photo/$value` — фото профілю, той самий scope
- `birthday` — дата народження; у схемі є, але в студентів майже ніколи не заповнена, тому вважаємо її заявленою користувачем під час онбордингу

Ці поля заповнює адміністратор вишу під час створення акаунта. Вони можуть бути заповнені повністю або порожні, і кожен тенант поводиться по-своєму. Перевірити це можна лише одним живим студентським акаунтом на виш.

**Недоступно ніколи:** рік навчання, номер групи, семестр, оцінки. Ці дані живуть у системах деканатів (eHMS, Wirtualny Dziekanat, e-KUL), жодна з яких не має публічного API.

## Провайдер 3 — Запасний Email OTP

Використовується, якщо адміністратор вишу вимкнув згоду користувачів на сторонні multi-tenant застосунки — тоді замість екрана згоди Entra повертає «Need admin approval».

1. Користувач вводить університетський email; домен звіряється з білим списком
2. Генерується шестизначний код; зберігаються його хеш, email і термін дії
3. Код надсилається листом; користувач вводить його
4. Перевіряються хеш, термін і лічильник спроб; видається сесія

Ліміти: 3 коди на email за годину, 10 на IP за годину, 5 спроб до спалення коду. Підтверджує лише володіння доменом — факультет і курс лишаються заявленими самим користувачем.

## Єдиний ендпоїнт авторизації

Веб і мобільний клієнт ніколи не звертаються до USOS, Entra чи поштового провайдера. Вони працюють з одним Go API Uniezz, який усередині спрямовує запит потрібному провайдеру.

### Публічний API

| Маршрут | Призначення |
|---------|-------------|
| `POST /auth/start` | Тіло: `{ university, provider? }`. Повертає URL редиректу обраного провайдера або запускає потік OTP |
| `GET /auth/callback/:provider` | Єдина точка зворотного виклику. Обробляє verifier від USOS, код авторизації Entra та введення OTP |
| `GET /auth/me` | Профіль поточної сесії |
| `POST /auth/logout` | Очищає сесію Uniezz |

`:provider` — одне з `usos`, `entra`, `otp`.

### Інтерфейс провайдера

Кожен провайдер реалізує один і той самий контракт:

```
AuthProvider {
  start(university)  -> URL редиректу або challenge
  callback(params)   -> NormalizedProfile
}
```

### Нормалізований профіль

Усі провайдери повертають одну структуру, тому решта застосунку не розгалужується за вишами:

```
NormalizedProfile {
  provider          usos | entra | otp
  providerUserId    стабільний ID від провайдера
  universityId      umcs | pollub | up | kul | wsei
  email
  firstName, lastName
  photoUrl?
  birthDate?        верифікована з USOS, інакше заявлена користувачем
  faculty?          верифікований, виведений або null
  programme?
  yearOfStudy?      лише UMCS
  verification      verified | directory | domain
}
```

### Рівні верифікації

| Рівень | Значення | Джерело |
|--------|----------|---------|
| `verified` | Підтверджено академічний запис | USOS API — UMCS |
| `directory` | Живий акаунт у каталозі вишу | Entra ID — решта чотирьох |
| `domain` | Лише володіння університетською поштою | Email OTP |

Рівень зберігається в профілі та відображається значком. Факультет і курс позначаються як підтверджені або заявлені для кожного поля окремо, а не для акаунта загалом.

### Додавання вишу

Новому вишу потрібен запис провайдера та ID тенанта чи інсталяції. Маршрути, робота із сесією та модель користувача не змінюються. Якщо Politechnika Lubelska, Uniwersytet Przyrodniczy, KUL або WSEI згодом нададуть доступ до USOS чи Moodle API, він підключається за тим самим ендпоїнтом, а наявні акаунти підвищуються з `directory` до `verified`.

## Модель сесії

- Токени провайдерів зберігаються лише на бекенді, браузер їх не бачить
- Фронтенд працює з cookie сесії Uniezz — `HttpOnly`, `Secure`, `SameSite=Lax`
- Дані профілю оновлюються під час входу та на запит, а не на кожному запиті
- Вихід очищає сесію Uniezz; авторизація у провайдера лишається, доки користувач не відкличе її в першоджерелі

---

## Безпека та приватність

- Consumer secret, client secret і токени доступу зберігаються в зашифрованому вигляді та не потрапляють до логів
- Запитується мінімальний набір прав, необхідний продукту
- PESEL та інші ідентифікатори, що надходять разом із датою народження, відкидаються під час читання і не зберігаються
- Користувач може від'єднати підключений акаунт і видалити профіль Uniezz
- Авторизацію у провайдера користувач може незалежно відкликати в USOSweb або у своєму акаунті Microsoft
- Обробка персональних даних відповідає GDPR: заявлена мета, мінімальний обсяг, видалення на вимогу

## Обмеження

- Рік навчання верифіковано лише для UMCS; в інших випадках він завжди заявляється самим користувачем
- Поле `department` може бути порожнім у будь-якому тенанті Entra, і без живого студентського акаунта це не з'ясувати
- Адміністратор тенанта може заблокувати згоду користувачів, що переводить виш на запасний OTP
- Politechnika Lubelska, Uniwersytet Przyrodniczy і WSEI тримають студентів та працівників в одному тенанті; їх розділення спирається на домен UPN або атрибути каталогу, жодне з яких не підтверджене без живого акаунта
- Підписування запитів OAuth 1.0a потребує бекенду; потік USOS неможливо реалізувати лише в браузері
- Politechnika Lubelska, Uniwersytet Przyrodniczy, KUL і WSEI працюють на eHMS, Wirtualny Dziekanat та e-KUL відповідно — жодна система не має публічного API

## Чекліст реалізації

1. Зареєструвати застосунок USOS на https://apps.umcs.pl/developers/ і покласти ключі в секрети бекенду
2. Зареєструвати multi-tenant застосунок Entra й обмежити його переліченими вище tenant ID
3. Побудувати єдині маршрути `/auth` та інтерфейс провайдера на Go API
4. Реалізувати провайдер USOS — триетапний OAuth 1.0a з підписом HMAC-SHA1
5. Реалізувати провайдер Entra, потім протестувати `$select` з Graph на одному живому акаунті кожного вишу та записати, які поля заповнені
